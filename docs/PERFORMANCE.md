# PERFORMANCE.md — 性能损耗对比

**简体中文** · [English](en/PERFORMANCE.md)

> 目标：把「混淆要付多少性能代价」从感觉变成**可复现的数字**，并给出选型建议。
> 本文数据以 **v1.1.1** 实测为主，并补充 **v1.1.3** 的 JIT 友好模式、**v1.1.4** 的 VM 内反调试、**v1.1.5** 的 VM 高级环境自检、**v1.1.6** 的原生状态机层与探针语法自检开销、**v1.1.7** 的 `low` 档去状态机与反 LLM 注释密度调整，**v1.1.8** 的 VM 符号名密文开销（见第 4 节），以及 **v1.2.11** 取消超级指令 `NOP` 占位后的字节码/内存变化（见第 15 节）。
> 本机 CLI、单核容器、PHP 8.5.12、OPcache 关（JIT 模式对比处另有说明）。复现命令见第 2 节。

---

## 1. 一句话结论

| 档位 | 运行时开销（TP8 真实接口） | 结论 |
|---|---|---|
| `min` | **贴近原生**（实测纯计算 1.01×；TP8 2.0 → 1.6 ms） | 词法替换 + 多方案字符串编码，**无反调试 / 无壳**，解码全走 PHP 原生函数 |
| `low` | **~2.8×**（→ 5.7 ms） | 可以直接上生产请求路径 |
| `mid` | **~6.2×**（→ 12.4 ms） | 可以直接上生产请求路径 |
| `high` | **~22×**（→ 44 ms） | 可用；建议只压核心文件，或前置页面缓存 |
| `max` / `ultra` | **~196× / ~242×**（→ 391 / 485 ms） | 离线任务、授权校验、关键算法片段；不要挂在高 QPS 路径上 |

**根因很单纯**：`high` 及以上才启用 **VM 虚拟机壳**——它把每条语句交给 PHP 写的解释器逐条执行，开销与「执行的语句数」成正比，而不是与「文件大小」成正比。`min` / `low` / `mid` 只有 token 级变换（`min` 连编码壳都没有），所以开销是常数级。

> 三个前提要一起看：
> 1. `min` / `low` / `mid` 三档**均不含 VM**（性能优先），要 VM 请上 `high`。
> 2. 从 v1.1.1 起 `low` / `mid` 的 token 级变换**大幅加强**（函数/类名、数字与字符串编码、
>    控制流 + GOTO、语义改写、运行时垃圾、诱饵注释、token 形态、EVAL/GZ 多壳），所以
>    它们的倍数比 1.1.0 的"轻量版"高，但仍然落在**个位数到十几毫秒**的绝对量级。
> 3. `min` 是「最接近原生」的档：变量名 / 数字形态 / 字符串多方案编码 / 去注释 / 压空白 +
>    编译时常量预计算，**无反调试探针、无壳、无复杂派生解密**——字符串解码全部走
>    `base64_decode` / `gzuncompress` / `chr` / `"\xHH"` 这类 PHP 原生能力，运行期不再有
>    PHP 逐字符循环。实测纯计算 1.01×、冷启动 1.05×，与原生同速。

## 2. 测量方法（可复现）

```bash
# A) 混合负载：测 token 级档（low / mid）
php tests/perf_bench.php --runs=5 --levels=min,low,mid

# B) 轻负载：测 VM 档（high / max）——混合负载在 VM 下会跑上几分钟
php tests/perf_bench.php --runs=5 --levels=high,max --workload=tests/perf_workload_vm.php

# C) 开 CLI OPcache 再测一遍（贴近 FPM + OPcache 的生产环境）
php tests/perf_bench.php --runs=5 --levels=low,mid --opcache
```

工作量脚本 `tests/perf_workload.php`（3.2 KB）覆盖：算术循环、用户函数调用、类方法调用、
数组构造/排序/关联遍历、字符串拼接与哈希、递归、闭包、生成器。产物与原生**必须输出同一
校验和**，否则该行标记 `✗`（语义被破坏时性能数字没有意义）。

指标口径：

| 指标 | 含义 |
|---|---|
| 冷启动总耗时 | `php <产物>` 的墙钟时间中位数，含 PHP 进程启动（本机 CLI 约 23 ms） |
| 纯计算耗时 | 工作量脚本内部 `hrtime` 自测，**不含**进程启动与解码，最能反映运行时开销 |
| 解码/编译开销 | 冷启动总耗时 − 纯计算 − 空脚本基线 ≈ 壳层解密 + eval 编译（FPM 下每请求都会付一次） |
| 峰值内存 | `memory_get_peak_usage(true)` |

**绝对数值只在同机对比时有意义**，倍数关系可跨机参考。

## 3. 运行时开销：混合负载（token 级档）

源文件 3.2 KB，原生纯计算 8.27 ms。3 次采样取中位数：

| 变体 | 产物体积 | 冷启动总耗时 | 纯计算耗时 | 计算相对原生 | 语义一致 |
|---|---:|---:|---:|---:|:---:|
| 原生（未混淆） | 3.2 KB | 32 ms | 8.27 ms | 1.00× | ✓ |
| `min` | 2.8 KB | 32.4 ms | 8.4 ms | **1.01×** | ✓ |
| `low` | 8.0 KB | 39 ms | 13.54 ms | **1.64×** | ✓ |
| `mid` | 16 KB | 38 ms | 14.43 ms | **1.74×** | ✓ |
| `high` | 82 KB | — | 167.8 s（单次实测） | ~20,000× | ✓ |

`high` 在这份负载上已经没法稳定采样（函数调用 + 字符串密集），但它**不是超时失败而是结论本身**：
VM 档请用下一节的轻负载衡量。实际使用中 VM 档只该压在被调用次数有限的核心文件上。

> 1.1.0 的 `low` / `mid` 是 1.17× / 1.49×，但那两档当时几乎没有 token 级变换。v1.1.1 把
> 「不随语句数增长」的保护全堆上之后是 1.64× / 1.74× —— 用不到 1 毫秒的纯计算增量，
> 换来函数名/类名/字符串/数字/控制流/形态全套混淆 + 多层壳。

## 4. 运行时开销：VM 档（含 1.1.0 → 1.1.1 解释器提速）

轻负载 `tests/perf_workload_vm.php`（1.8 KB，原生纯计算 **0.919 ms**），3 次采样中位数：

| 变体 | 1.1.0 纯计算 | 1.1.1 纯计算 | 相对原生 | 语义一致 |
|---|---:|---:|---:|:---:|
| 原生 | 0.919 ms | 0.919 ms | 1.00× | — |
| `high` | 10,244 ms | **5,676 ms** | 6,176× | ✓ |
| `max` | 14,476 ms | **8,120 ms** | 8,836× | ✓ |

同一份产物在「20 万次 while 循环」这类**状态机派发密集**负载上（原生 1.20 ms）：

| 档位 | 1.1.0 | 1.1.1 | 提速 |
|---|---:|---:|---:|
| `high` | 5,655 ms | **2,198 ms** | **2.6×** |
| `max` | 6,769 ms | **2,678 ms** | **2.5×** |

提速来自两处（都在解释器热路径上）：

1. **操作数栈编码类型化**（占旧实现 VM 总耗时约 75%）：旧版把**每个**压栈值 `serialize()`
   后用 `str_repeat` + `substr` 现算 XOR 掩码、出栈再 `unserialize()`；新版按类型分流——
   int 走单次整型 XOR、string 走单次串 XOR（掩码从 8 KB 预算 pad 取）、float/bool/null 直存、
   array 才 serialize、不可序列化值落明文槽。解码内联进 `MCPOP`/`MCPEEK`，省掉一次闭包调用
   （≈ 26 ns/指令）。
2. **状态机派发压缩**：新增 `DISPATCH` / `SET_ST` 两条专用指令，把
   `PUSH_V st; PUSH_C s; EQ; JZ 1; JMP` 五条压成一条、状态写入两条压成一条。

倍数看着夸张（数千倍），是因为这份负载**几乎全是纯计算与函数调用**（没有 IO、没有框架开销）。
真实业务代码里框架启动、DB、模板渲染占大头，倍数会被稀释——见下一节。

**v1.1.3 新增 JIT 友好模式（不改栈式架构，再省一层闭包调用）**：从 1.1.3 起操作数栈编码逻辑**内联进 `MCPUSH` 闭包**、整段解释器保持平坦大函数，去掉旧实现 `MCPUSH → MCENC` 的嵌套闭包调用。实测（隔离栈编码路径、2M 次压栈密集循环、CLI 关 OPcache JIT、5 次采样中位数）：

| 模式 | 纯计算耗时（2M 压栈循环） | 相对 nojit | 语义一致 |
|---|---:|---:|:---:|
| jit 内联（默认开） | **64.05 s** | **1.00×** | ✓ |
| nojit 闭包（回退） | 66.82 s | 1.04× | ✓ |

jit 内联模式**约快 4%**，且平坦函数更易被 OPcache tracing-JIT 追踪编译；两种模式对象均走明文槽 `$___MCPLAIN___`（flag1，按引用返回），属性写回不丢。`--no-vm-jit` 可回退旧闭包栈（语义逐字节等价）。需说明：该 VM 是「每指令一次闭包调用」的 PHP 实现，OPcache tracing-JIT 对整体提速有限（跨闭包难深度内联），jit 模式的价值主要在「平坦函数更易被 JIT 接纳 + 省一层闭包调用」，**对第 1 节各档位端到端总开销（TP8 真实延迟）影响在个位数 % 内、不改变「数量级」结论**，故第 1 节表未单列 jit 列。

**v1.1.4 的 VM 内反调试开销**：dispatch 循环内每 512~8192 条指令复检一次（一次自增 + 按位与 + 未命中即跳过），未命中时**不产生额外分支**；命中检测本身（`PHP_SAPI` 比较 / `extension_loaded`）摊销到数千条指令，可忽略。整体在 VM 总耗时中的占比 **<3%~5%**（≈2~3 ns/指令）。正常环境污染因子恒 0，opcode 解码结果不变，**不改变第 1 节各档位延迟的数量级结论**；`--no-vm-inloop` 可完全关闭。

**v1.1.5 的 VM 高级环境自检开销**：初始化处一次 `defined+constant+hash('sha256')`（≈0.3 µs，摊到整个进程可知觉不到）；dispatch 循环内的周期复检**复用 v1.1.4 已有的检查点**（不新增分支、不新增计数器），故额外成本仅为「每 512~8192 条指令多算一次 sha256」≈0.3 µs / 数千条指令，**占比 <0.1%**。正常环境 `PZ0` 恒 0，opcode 解码结果与本版之前逐字节一致；`--no-vm-selfcheck` 可关闭。另注：污染态收尾新增的 `is_array(...)&&count(...)` 只在解释器**退出前**执行一次，不在热路径上。

**v1.1.6 的原生状态机层开销**：状态机是**语句级**改写（不是逐指令），成本主要在两处——
① **构建期**：每个被包裹的语句段做一次 token 切分 + 重排（`StatementSplitter::splitRanges`），
属一次性开销，与源文件规模线性相关；② **运行期**：分发器把「顺序执行 N 条语句」变成
「N 次状态跳转」，每条语句额外一次整数比较 + 一次赋值（约 5~15 ns/语句）。
对典型业务文件（数百条语句）即**微秒级**，相对文件整体执行时间可忽略。
`--sm-passes=1` 时**不产生嵌套分发树**（只有一层），开销最低；`--sm-complexity` 越大，
每分发器容纳的语句越多、跳转次数越少。建议：`mid` 档用默认（8/2/2），
对性能敏感的服务端可用 `--sm-passes=1 --sm-complexity=16` 折中。

**v1.1.6 的探针语法自检开销**：每个探针组在构建期跑一次 `php -l`（子进程，约 15~30 ms/组）。
最多 8 组 → 构建期额外 **~0.1~0.25 s**，一次性、不影响运行期。
这是为消除「构建期零告警、只有跑产物才 Parse error」这类事故而付的必要成本。

**v1.1.7 的开销变化**：

1. **`low` 档移除 `statemachine` 层**——构建期少一次 token 切分 / 重排，运行期不再有
   「N 次状态跳转」的整数比较 + 赋值（约 5~15 ns/语句），`low` 档运行期开销进一步贴近原生。
   `mid` / `max` / `ultra` 的状态机参数未变（`high` / `min` 本就未接入），
   故第 1 节这三档数据不受影响。
2. **反 LLM 互斥注释密度提升**（每层壳 3/6/12 簇）——注释**不产生任何运行期指令**，
   运行期开销恒为 0；仅构建期多一次 `token_get_all` + 安全边界扫描与文本填充，
   对典型业务文件为毫秒级，且白名单过滤后实际投放量受安全边界数限制，不会无限增长。
3. **VM 运行期私有 / 受保护方法改用 `ReflectionMethod::setAccessible(true)`**——
   仅在调用真实类方法时多一次反射对象构造（微秒级、非热路径），字节码解释器主循环不变，
   第 1 节各档位开销的数量级结论不变。

**v1.1.8 的 VM 符号名密文开销**：实测（同一夹具、同一 salt、交替顺序各 15 次取均值）——
产物大小 **54092 → 54260 字节（+0.31%）**，运行耗时 **on 112.4 ms/次 vs off 112.4 ms/次**
（差异 **< 1%**，被测量噪声淹没，实测不可分辨）。

原因是该特性的成本是一次性的、且不在热路径上：
- **构建期**：每个符号一次 `base64(XOR)`，几百个符号合计 **< 1 ms**；
- **运行期**：解包时每个符号一次 `base64_decode` + 一次 XOR 循环，同样 **< 1 ms**，
  之后 program 与旧版逐字段相同，解释器主循环**一行代码都没变**；
- **体积**：符号串在容器里占比很小（容器大头是指令操作数），且外层 gzip 会吃掉一部分
  base64 冗余，故净增仅 0.3% 量级。

结论：**这一版对性能与产物体积基本无感知**，可放心默认开启。

**v1.1.8 的容器格式随机化开销**：可忽略到不可测——
- **构建期**：6 次 `deriveInt` + 一次 6 元素数组装配（**纳秒级**）；
- **运行期**：产物里多一张 6 元素的映射表（`$___TM___`），每次读一个类型标记时多一次
  **数组查表**（哈希查找，~50 ns/次）。相对 VM 解释器每条指令的开销（百 ns~微秒级）
  占比 **< 0.1%**；
- **体积**：映射表本身 < 200 字节，且被外层 gzip 有效压缩，净增 **< 0.1%**。

**v1.1.8 的「无 salt 随机盐兜底」开销**：可忽略——每次构建多一次 `random_bytes(16)`
（纳秒级），换来的是无 salt 路径与指定 salt 路径**完全同源**（走同一套确定性派生分支，
消除长期缺乏测试的 `random_*` 兜底分支）。指定 `--salt` 时该逻辑完全不触发。

## 5. 真实项目：ThinkPHP 8 页面延迟（v1.1.1 五档）

同一套 TP8 示例（22 文件 / 16 类，含 ORM / 事务 / 缓存 / 中间件 / 验证器 / 事件），
原版与混淆版各起一个 `php -S`、各用**自己的 SQLite 库**、同一份 seed 数据，
`GET /shop/products`（缓存 + 获取器 + JSON 字段 + 关联统计）取 5 次中位数：

| 变体 | 延迟 | 相对原生 | 产物体积 |
|---|---:|---:|---:|
| 原生 | 2.0 ms | 1.0× | — |
| `min` | **1.6 ms** | **0.8×（更快）** | 104 KB |
| `low` | 5.7 ms | 2.8× | 228 KB |
| `mid` | 12.4 ms | 6.2× | 412 KB |
| `high` | 44 ms | 22× | 2.1 MB |
| `max` | 391 ms | 196× | 3.3 MB |
| `ultra` | 485 ms | 242× | 6.8 MB |

> `min` **比原生还快**不是测量错误：它做了「去注释 + 压空白」，PHP 解析与 opcache 编译的
> 字节数变少，而新增成本只是每串一次原生 `base64_decode` / `gzuncompress` / `chr` 装配
> （多方案混合，无 PHP 逐字符循环），与去注释/压空白省下的编译字节数相抵，净收益为正。
> 这也意味着 `min` 是**唯一可以无脑全站铺开**的档位——它**无反调试探针、无 `eval`、
> 无 `gzinflate`、无输出缓冲**，解码全走 PHP 原生函数，运行时仍是普通 PHP 文件。

> 两轮独立复测（各自独立库 + seed + 预热）以确认稳定性：`mid` 11.12 / 11.13、`high` 44.4 / 45.7、
> `max` 395 / 409、`ultra` 473 / 476（ms）；`low` 波动较大（6.3 / 8.2），因其解码成本已接近
> PHP 启动抖动本身。**`max` / `ultra` 的早期版本曾按 `high` 的倍率估算（~46× / ~60×），
> 实测比估算慢 5 倍**——多出来的 `anti_ast` / 蜜罐 / 换行缠绕 / 结构毒化 / 防篡改壳每请求都要
> 做一遍解码与完整性校验，这部分成本与业务代码量无关，是**每请求固定开销**。

三点观察：

1. **绝对延迟是毫秒级，不是分钟级**——TP8 页面真正的开销大头（框架启动、DB、渲染）在 VM
   之外，VM 只解释业务代码那部分。50 ms 级延迟对后台/内部系统完全可接受。
2. **`min` 与原生同速甚至更快**，`low` / `mid` 落在 **6~12 ms**，与原生同处一个量级，
   可直接挂生产请求路径。`high` 的 44 ms 仍属可接受；`max` / `ultra` 的 391~485 ms 是
   **每请求固定开销**（多层壳解码 + 完整性校验），适合低频高价值入口，不适合高频接口——
   它们的定位本就是「单文件 / 核心算法」而非整站。
3. 11 个端点在**六档下全部逐字节等价**（含 POST、缓存、聚合、签名中间件 401 分支），
   说明这些数字对应的产物是**语义正确**的。早期的 high/max 空正文问题已在 1.1.1 修复
   （见 CHANGELOG）。

## 6. 开销归因：钱花在哪个开关上

同一份「20 万次算术循环」负载（原生纯计算 1.4 ms，进程启动基线 ~23 ms），逐个开关单独打开：

| 变体 | 冷启动总耗时 | 相对原生 | 说明 |
|---|---:|---:|---|
| 原生 | 24 ms | 1.0× | 基线（含 23 ms 进程启动） |
| 仅变量改名 `--var-length=8` | 25 ms | ~1.0× | **几乎免费** |
| 变量改名 + `--junk-runtime`（强度 8） | 25 ms | ~1.0× | 运行时垃圾可忽略 |
| `--vm`（裸 VM） | 1,640 ms | ~68× | **VM 一开就跳两个数量级** |
| `--vm --vm-junk=80` | 1,991 ms | ~83× | 字节码垃圾真实执行，+21% |
| `--vm --vm-p8` | 1,596 ms | ~66× | morph/keychain/builtinReplace 基本不加运行时 |
| `--vm --vm-junk=80 --vm-p8` | 2,240 ms | ~93× | 叠加后约 +37% |
| 预设 `low` | 25 ms | ~1.0× | 无 VM |
| 预设 `mid` | 26 ms | ~1.1× | 无 VM |

结论：

- **VM 是唯一"数量级"开关**，其余（变量/函数/类改名、字符串 XOR、数字编码、控制流 + GOTO、
  语义变换、运行时垃圾、逐层壳）都是**常数级或可忽略**——1.1.0 → 1.1.1 把 `low`/`mid`
  加到"几乎全开"，纯计算只从 1.17× 涨到 1.64× 就是证据。
- `--vm-junk` 是 VM 内部唯一明显加运行时成本的参数（垃圾指令是**真执行**的，不是跳过）。
- `morph` / `keychain` / `builtinReplace` / `probe` / `fakeFog` 主要加**体积与构建时间**，
  运行时几乎不变——这几个是"性价比最高"的加固项。
- `--vm-probe` 的探针、`anti_debug` / `anti_tamper` 自校验是**每请求一次**的固定成本，
  不随业务量线性增长。

## 8. 选型建议

| 场景 | 建议 | 理由 |
|---|---|---|
| 高频 Web 接口、内部系统 | `low` 或 `mid` | 毫秒级开销，但已含函数/类/字符串/数字/控制流全套混淆与多层壳 |
| 对外分发的组件 / SDK | `high` | 值得付数十倍代价换取 VM 保护 |
| 授权校验、计费算法等核心片段 | `max`（只混淆该文件，其余用 `mid`） | 把 VM 代价限制在少量文件上 |
| CLI 批处理 / 离线任务 | `max` / `ultra` | 不在乎运行时，追求最强保护 |
| 框架项目（ThinkPHP / Laravel 等） | 直接用预设即可（五档均已验证） | v1.1.1 起预设默认保留属性名/参数名，框架按名读写的属性与路由参数不会被破坏 |

**分层混搭**是最实用的做法：把 `max` 只压在少数核心文件上，其余文件走 `mid`。

```bash
# 核心文件强保护
php entry.php --input=app/service/PriceCalculator.php \
    --output=dist/service/PriceCalculator.php --level=max --salt=$SALT

# 其余文件低成本混淆
php entry.php --input=app/controller --output=dist/controller --level=mid --salt=$SALT
```

## 9. 已知性能特性（不是 bug，是设计）

1. **VM 开销 ∝ 执行语句数**，与文件大小关系不大——一个被调用 10 万次的小函数比一个只加载一次的大文件贵得多。
2. **函数/方法调用是 VM 最贵的操作**（帧建立 + 参数绑定 + 引用回写）。调用密集的代码在 `high` 下会显著放大。
3. **生成器 / 大数组**在 VM 下内存占用更高（实测峰值 6 MB vs 原生 2 MB）。
4. **解码是每请求一次**：无 OPcache 时 eval 的代码不进字节码缓存，FPM 下每个请求都要重新解密 + 编译外层壳。若 QPS 高，务必开 OPcache 并考虑 `--opcache` 预热。
5. 想关掉某个拖慢的开关：`--vm-junk=0`、`--no-vm-cpool`、`--no-newline-poison`、`--no-shell-shield`（后者最影响体积与解码时间）。
6. **VM 档下用户函数被编译为字节码**，不再是 PHP 函数：`function_exists()` / 字符串回调
   （`call_user_func('name')`）由 VM 内部解析（v1.1.1 起兼容 `App\Util\name` 这类绝对名）。
   依赖反射遍历用户函数的代码在 VM 档下会看不到它们——这类代码请用 `low` / `mid`。

## 10. v1.2.5：超级指令 / 常量预计算 / 函数打散

**超级指令（`--vm-super-isa=N`）** 减少主循环次数：一条复合指令一次取指、一次 dispatch 就执行完 2~4 条子指令。40 万次算术循环实测（裸 `--vm`，每档 3 次取最快值）：

| `--vm-super-isa` | 纯计算耗时 | 相对关闭 | 产物正确 |
|---|---:|---:|:---:|
| 0（关） | 1.96 s | 1.00× | ✓ |
| 3（默认） | 1.93 s | 0.98× | ✓ |
| 8 | 1.94 s | 0.99× | ✓ |
| 16 | 1.97 s | 1.01× | ✓ |

**收益在测量噪声量级（±2%）**：省掉的是每条子指令的一次主循环迭代（数组取值 + 两次异或 + 跳转表查表 + `switch` 分派，约几十 ns），但复合 handler 内部仍要逐条执行子指令的操作数解码与栈访问，这部分才是 VM 的主要成本。所以它的定位不是"提速"，而是**抗分析 + 零代价**——字节码里出现陌生 opcode、指令频次统计失效，而合并本身不增加运行开销，故默认开启（3 条）。构建期只多一次 n-gram 统计与逐段替换，实测 `mixed_advanced.php` 0.27 s → 0.29 s。

> **v1.2.11：取消 `NOP` 占位，改为"真删 + 重算位置"。** v1.2.5~v1.2.10 用 `NOP` 填充被吸收
> 的位置，好处是段内指令条数不变、跳转与异常表零重算；代价是字节码里留下一大簇 `NOP`
>（这本身就是"此处被合并过"的显眼指纹），且解包后数组白白多出这些元素。v1.2.11 改为把
> 被吸收的子指令**直接删除**，构建期按「旧索引 → 新索引」映射重算段内所有相对跳转偏移，
> 以及异常表 `[tryStart, tryEnd, handlerPc]` 三个绝对 pc（跳转目标与异常表端点列为
> "不可跨越"位置，合并绝不横跨它们，因此映射必然精确）。实测见第 15 节。

**常量预计算（`constfold`）** 只影响**构建期**：纯字面量表达式在构建期算完并替换为字面量，产物体积**变小**（token 更少），构建耗时增加毫秒级，运行期开销**为负**（这段计算彻底消失）。`min` 档因此零成本收益，预设已默认带上。

**函数打散（`funcsplit`）** 把一点工作量从「内联语句」挪到「一次函数调用」：
- 运行期：每个被提取的代码块多一次用户函数调用（约 0.1~0.3 µs，主要是参数绑定）；PHP 调用开销不大但不为零，`func_split_level=3` 落在热点内循环上可测量；
- 构建期：每文件一遍 token 扫描 + 作用域分析（线性），可忽略；
- 体积：略增（函数定义 + 参数列表），语句密集文件典型 **+2~4%**；
- 实践建议：请求路径代码用 1~2 级；3 级适合离线脚本与授权/算法片段——那里可读性比微秒更重要。

**整站构建（生产不建议）** 的数据见 `CHANGELOG.md` v1.2.5：WordPress（1516 个 PHP 文件 / 119 MB）`min` 档构建约 15 s，产物全量 `php -l` 通过；ThinkPHP 8 表现相同。这些都不改变第 1 节结论：**VM 仍是唯一「数量级」开关**，v1.2.5 新增的三项都在常数级。

## 11. v1.2.6：等价 ISA 拆解 / 三分支诱饵 / 解释器混淆

**等价 ISA 拆解（`--vm-isa-split=N`）** 是本节唯一"真·零成本"项。40 万次算术循环（裸 `--vm`，每档 3 次取最快值）：

| `--vm-isa-split` | 纯计算耗时 | 相对 1 | case 标签数 |
|---|---:|---:|---:|
| 1（关） | 1.95 s | 1.00× | 28 |
| 2（默认） | 1.95 s | 1.00× | 36 |
| 3 | 2.00 s | 1.03× | 40 |

关键实现是**同一语义的多个 case 标签共用一份 handler 体**（`case A: case B: body`），而不是复制多份 —— 字节码里确实出现多个功能相同的 opcode 且都在轮转使用，但生成的 PHP 代码量几乎不变、I-cache 压力不变，派发仍是一次跳转表哈希查找，因此 split=2 的损耗落在测量噪声内。split=3/4 时 case 表进一步增大，约 2~3% 噪声级波动；默认 2 兼顾效果与零成本。

**三分支诱饵（`decoy` 层）** 的运行期成本是**每个被改写语句一次** `is_scalar()` + 若干纯函数（`strlen` / `crc32` / `count`）+ 一次比较，典型几十 ns；真分支里的"同理替换"只是多几个局部变量赋值，不改变算法复杂度。构建期是一遍线性 token 扫描。密度由 `--decoy-level` 控制（12% / 25% / 45%），`high` / `max` / `ultra` 预设默认带上。

**函数打散（`funcsplit` 等级 3 的 stmt 模式）** 把写回语句也搬进顶层函数，每个被提取的块多一次用户函数调用（约 0.1~0.3 µs）。与 v1.2.5 的建议一致：请求路径代码用 1~2 级，3 级适合离线脚本与授权/算法片段。

**解释器本体混淆** 全部是编译期等值变换（十进制 `→` 十六进制、ASCII 串 `→` `\xHH`），加上恒假的不可达伪块；对热路径的 opcode 与执行顺序没有任何改变，运行期开销为零，构建期只多一遍 token 重写。

整站 max 档的实测（只做 `php -l`，不执行业务代码）见 `CHANGELOG.md` v1.2.6。

## 12. v1.2.7：并行构建 + 整站 max 运行实测

**并行工程构建**（`--jobs=N`，需 `pcntl`）：全局符号表在 Pass 1 只建一次，N 个 worker 进程
用 fork 并发混淆互不重叠的文件子集，各自写独立输出、经小计文件汇总计数。实测同一台 32 核机：
525 文件的 ThinkPHP 8 夹具，`max` 全量分层串行约 **12 分钟**，`--jobs=32` 约 **3.5 分钟**
（约 3.4×）；官方白名单模式因 framework 目录原样拷贝、只深混 app/，约 **10 秒**完成。
jobs≤1 或无 pcntl 时零变化退回串行。

**运行期开销不变**：本版改动均为构建期正确性修复 + 并行化，不改变任何 opcode / 壳层运行逻辑。
`mixed_html_skip_aggressive` 仅对混写模板少做两个构建期变换层，运行期产物更短而非更慢。

**整站实测口径升级**：从 v1.2.6 的「只做 `php -l`」升级为「逐文件独立进程执行、stdout +
exit code 与原生逐字节比对」。525 文件夹具 524/525 stdout 逐字节一致；唯一差异是
`public/index.php` 独立 include 时防御壳 shutdown 静默置 rc=1（stdout 仍逐字节一致，
Web SAPI 正常请求不误报），属已知的「脱壳独立运行」边界。详见 `CHANGELOG.md` v1.2.7。

## 13. v1.2.8：零 eval 循环折叠 / Logic 前置剪枝 / VM 解释器混淆

**构建期纯计算循环折叠（`loop_fold`，默认开）**：把"字面量边界 + 纯确定性字面量运算"的循环
在构建期用 `ConstEval`（token 级符号执行器，调用 PHP 原生运算符，**完全不用 eval**）算完、
替换为结果字面量，运行时不再迭代。在线混淆服务器场景下，`eval(用户上传 token)` = 免费
webshell 注入器，本版把该注入面彻底移除。同一份 `tests/perf_workload.php`（含 20 万次算术
循环，原生纯计算约 12 ms），每档 5 次取中位数：

| 变体 | 纯计算耗时 | 相对原生 | stdout 逐字节一致 |
|---|---:|---:|:---:|
| 原生（未混淆） | ~12.1 ms | 1.00× | — |
| `min` + 循环折叠 | **~8.56 ms** | **0.71×（更快）** | ✓ |
| `min` + `--no-loop-fold` | ~12.99 ms | 1.07× | ✓ |

折叠后比原生还快约 30%——20 万次循环在产物里被整段替换成一个结果字面量，运行期零迭代。
安全边界（token 白名单 / 迭代上限 100 万 / 双次严格比对 / liveness 回写 / 失败原样保留 /
零 eval）确保只有完全确定的纯计算循环被折叠；负载里其余含函数调用 / 闭包的循环保持不动。
`--no-loop-fold` 一键关闭。

**激进恒等式压缩 + 死分支剪枝前置（`--aggressive-prune` / `--level=aggressive`，默认关）**：
本版把该层从 Logic 之后移到 **Logic 之前**——只折叠用户自己的恒等式与死分支，绝不折叠
混淆器注入的恒等式（不给攻击者送去混淆工具）。计算密集负载的运行时开销下降；可选层，
min~ultra 各档不受影响。`aggressive` 预设（ultra 全保护 + 本层）端到端输出逐字节一致。

**VM 解释器 Logic 混淆（新增）**：解释器的整数字面量改成编译期位运算恒等式
`N → ((Ka) ^ (Kb))`（salt 派生、可复现），opcode 数字从解释器源码消失。这些是合法常量
表达式（case 标签 / 数组索引 / 默认参数均可用），编译期求值、运行期零成本，不改动第 1 节
各档延迟结论。`break`/`continue` 层级操作数（PHP 要求整数字面量）跳过；
`--no-vm-runtime-logic` 可退回 v1.2.6 的十六进制形态。high/max/ultra/aggressive 逐字节一致。

**Logic 层加强**：LogicRewriter / DecoyBranches 保持安全强度顶格（intensity / decoy_level=3，
OOM 的 wild 仍可选），新增 4 种恒真/恒假诱饵模板增加分支多样性。

**运行时 KDF 保持原算法**：本版撤销了早前的 KDF 降级——StructPoison rounds 恢复 3
（ultra/aggressive=5）、VM 常量池无预算 SHA-256 流、蜜罐 1.4 s 忙等无条件。各档逐字节一致。

## 14. max 档运行期性能杀手定位（v1.2.8 实测）

用 `tests/perf_workload.php`（纯计算、覆盖算术/函数/类/数组/字符串/递归/闭包/生成器）作输入，
逐层剥离 + 硬超时实测，定位 max 档产物**运行期**（不是构建期）的开销来源。

### 14.1 测量方法

- 产物 = `php entry.php --input=tests/perf_workload.php --level=max --salt=perfkill`；
- `COMPUTE` = workload 内部 `hrtime` 自测的纯计算耗时，`WALL` = `php 产物` 墙钟；
- 逐层剥离：从 max 预设中注释掉单层后重建，比较 `COMPUTE` 变化；为排除 LoopFold 掩盖效应，
  另做一组"统一关闭 constfold"的对照。

### 14.2 关键数据

| 变体 | WALL | COMPUTE | 产物体积 | 结论 |
|---|---:|---:|---:|---|
| 原生 workload | 0.04 s | 11.6 ms | 3.6 KB | 基线 |
| max（开 constfold，默认） | 0.20 s | 152.6 ms | 168 KB | 计算放大 **13×** |
| max（关 constfold） | — | 682.9 ms | 162 KB | 折叠掩盖了放大：动态代码放大 **59×** |
| max **去掉 logic 层**（其余不变） | 0.06 s | **15.4 ms** | 62 KB | **回落至接近原生** |
| max 去掉 string 层 | — | 83.5 ms | 144 KB | 次要因素 |
| max 去掉 VM 层 | 0.20 s | 159.7 ms | 62 KB | 无改善，VM 不是杀手 |
| max 关 cpool KDF / VM Logic / JIT / combo / super-isa / inloop | 0.20 s | 149–163 ms | — | 均无改善 |

逐层剥离（统一关 constfold，基准 682.9 ms）：logic→**25.0 ms**、string→83.5 ms，其余
（junk_runtime / decoy / statemachine / semantic / controlflow / funcsplit / func / var /
number / token）剥离后仍在 678–699 ms，无实质改善。

### 14.3 结论：logic 层的常量恒等展开是真正的运行期杀手

`LogicRewriter`（intensity≥1，即所有非 min 档）会把循环体里的**每个数字/字符串字面量**
改写成含运行期函数调用的恒等表达式：

- 数字：`N → strlen(sha1('…'))*b + strlen(md5('…'))*a + strlen('…')`；
- 字符串：`'s' → base64_decode('…') . hex2bin('…') . str_rot13('…')`。

于是 `for(…){ $sum += ($i*3)%7; … }` 里的 `3`、`7` 每次迭代都要真算一次 sha1/md5，
20 万次循环放大成数十万次哈希调用——这就是 13×（无折叠时 59×）的来源。

**澄清两点**：

1. **不是 KDF**：关掉 VM 常量池 KDF、StructPoison、蜜罐忙等后计算耗时不变（149–163 ms）；
   运行期 KDF 是一次性解码开销的一部分（约 30 ms），不随循环增长。
2. **不是 VM**：VM 逐条解释本身在此负载下开销有限（去 VM 反而 159.7 ms）；JIT / combo /
   super-isa / inloop 等内部开关对计算耗时几乎无影响。

**为何平时感知不明显**：默认开 `constfold`（LoopFold），20 万次循环在构建期被静态折叠成常量，
掩盖了 logic 的放大（152 ms vs 683 ms）；一旦遇到**无法静态折叠的动态代码**（依赖输入、
超迭代上限、含非白名单运算），logic 层的放大就会完全暴露。

**可选的缓解口径（仅说明，未改动默认配置）**：对计算密集且需运行期性能的文件，可用
`--level=mid`（无 logic 强度 3 / 无 VM）或降低 logic intensity / 关闭 logic 层；代价是
混淆强度下降。默认 max 为保护强度优先，维持现状。

### 14.4 附带发现：high 档产物卡死 —— 已在 v1.2.9 修复

同一批实测中，`high` 档产物在 `timeout 15/30` 下均**零输出、超时退出（exit 124）**，
而 max/ultra/mid 正常。v1.2.9 已定位并修复：

- **现象**：进程 `RN` 态 CPU 空转，gdb 抓栈停在 `php_var_serialize()` —— VM dispatch 循环
  反复压栈序列化，形成死循环；逐层剥离显示只有去掉 `shell:vm` 才恢复正常。
- **根因**：`high` 在 `shell:vm` **之前**的层与 `max` 不同（缺 `decoy`/`statemachine`、`goto`
  仅 3），送入 VM 编译器的 token 流形态不同，含循环的代码被编成跳向负 PC 的坏相对跳转
  （如 `[1394,-77]`）。部分 salt 下 dispatch 空转死循环，另一些 salt 下静默算错循环累加值
  （如 `S=0` 而非 `S=29992`）。
- **修复**：`high` 的 VM 前置层现在与 `max` **完全一致**（含 `decoy`、`statemachine`、`goto=4`），
  走同一条已验证的 VM 编译路径；档位差异仅保留在 VM 参数（chunks 8 / probe 12 / fog 80 /
  isaSplit 2）与后续编码壳层数，high 强度仍弱于 max。perfkill / v129high / abc123 / x 等
  历史坏 salt 与多个负载全部逐字节一致，`tests/v129_features.php` 覆盖此回归。

## 15. v1.2.11：超级指令取消 NOP 占位（真删 + 重算位置）

**改了什么**：v1.2.5 起超级指令合并时用 `NOP` 占位补齐，使段内指令条数、索引完全不变，
因此跳转偏移与异常表 `pc` 区间**无需重算**——实现简单、风险低，但会在字节码里留下与合并
次数等量的 `NOP`。v1.2.11 改为把被吸收的子指令**直接删除**，并在构建期同步重算：

- 段内所有相对跳转（`JMP` / `JZ` / `JNZ` / `DISPATCH`）的偏移；
- 异常表每条记录的 `[tryStart, tryEnd, handlerPc]`。

跳转目标与异常表端点会先被收集为"不可跨越"位置，任何合并区间只要跨到它就直接放弃，
因此端点在新索引里必有精确映射（不存在"落在合并区间内部"的歧义）。

**测量条件**：`tests/perf_workload_vm.php`（3.2 KB，算术循环 / 函数 / 类方法 / 数组 /
字符串哈希 / 递归 / 闭包 / 生成器），`--salt=perf-bench-v1`，PHP 8.5.12 CLI、OPcache 关，
两版各跑 5 次取中位数，产物与原生校验和必须一致。峰值内存用 `memory_get_peak_usage(false)`
（精确口径；`true` 按分配块取整，只看得到 6 MB 这一档，分辨不出差异）。

| 指标 | v1.2.10 | v1.2.11 | 变化 |
|---|---:|---:|---|
| 字节码指令总数（`high`） | 565 | 454 | **−111（−19.6%）** |
| 解包后峰值内存（`high`） | 3,961,416 B | 4,625,640 B | +664,224 B（+16.8%） |
| 解包后峰值内存（`max`） | 4,733,264 B | 5,431,272 B | +698,008 B（+14.7%） |
| 纯计算耗时（`high`） | 16.88 ms | 17.17 ms | +0.29 ms（+1.7%） |
| 冷启动总耗时（`high`） | 63.3 ms | 62.7 ms | 噪声内 |
| 产物体积（`high`，gz+分片加密） | 74,243 B | 74,375 B | +132 B（+0.18%） |
| 产物体积（`max`） | 86,047 B | 87,407 B | +1,360 B（+1.58%） |

**怎么读这张表**（注意：这一版的两项改动方向相反，别把账记到 `NOP` 头上）：

- **指令数 −19.6% 纯属 `NOP` 删除**。合并后不再留空元素，字节码里也没有成簇 `NOP`——
  静态分析里"这里被超级指令合并过"的显眼指纹随之消失。
- **内存 +15~17%、耗时 +1.7% 不是 `NOP` 的代价，而是同一版里那组 VM 兜底修复的代价**
  （见 15.1）。修复前这些语句退化成 `EVAL_STMT`：运行时只多一条字符串常量，交给原生
  `eval` 执行；修复后它们真的编进字节码，变成几十条 opcode 数组，而 PHP 数组的开销远大于
  一个字符串——于是解包后常驻内存变大，解释执行也比原生 `eval` 慢一点。
- 换句话说：**`NOP` 删除本身仍然是净收益**（指令更少、更干净），而"把更多语句编进 VM"
  是拿内存和 1~2% 的运行时间，换回**语义正确**（此前那些语句里的 `global`、对象方法调用、
  位运算会静默出错或直接致命，见 15.1）。
- **gz 后体积略增 0.2%~1.6%**：`NOP` 是 `[199][0]` 两字节的高度重复序列，gzip 几乎不占
  空间；去掉后相邻字节熵升高，压缩率略降。若极端在意分发体积，可用 `--no-vm-super-isa`
  关掉这一层（体积回到未合并状态，同时失去超级指令的提速与抗频次统计）。

### 15.1 同一版里顺带修掉的四处 VM 语义缺陷

这些都是 **v1.2.10 及以前就存在**的缺陷，`high` / `max` / `ultra` 会踩到，症状是"输出对不上
原生、且没有任何报错"：

| 缺陷 | 触发条件 | 修法 |
|---|---|---|
| 不透明载荷里的顶层变量没进 `$GLOBALS` | `shell:vm` 遇到无法直编的源码（`case(表达式)` 标签、命名空间块等）整体改走载荷 `eval`，载荷里的函数用 `global $x` 只能读到 `null` | `PHPRUN` 执行前扫载荷里的 `global $a, $b;` 与 `$GLOBALS['k']`，把对应名字预先绑成 `$GLOBALS` 的**引用** |
| 位与 `&` 编译失败 | `$x = $a & $b;`——只认了 `T_AMPERSAND_NOT_FOLLOWED_BY_VAR_OR_VARARG`，右操作数是变量时 token 形态不同 | 三种 `&` 形态都接受 |
| 裸块语句 `{ ... }` 不支持 | `logic` 层的临时变量缠结会生成这种分组 | 当作语句组递归编译（PHP 里裸块不引入作用域） |
| `__NAMESPACE__` 不支持 | `funcsplit` 的幂等守卫 `if(!function_exists(__NAMESPACE__ . "\f")){...}` | 编译期折值为当前命名空间（全局为空串） |

配套再加一条：`funcsplit` 不再抽取含 `->` / `?->` / `::` 的语句。抽出来的函数是**原生**
PHP 函数，而带 VM 的档位里用户类运行期是 `stdClass + META` 代理，语句一旦被搬进原生函数，
`$obj->m()` 就是 `Call to undefined method stdClass::m()` 致命。

**为什么值得付出内存**：`tests/preset_e2e.php`（六档 × 三夹具 × 构建/lint/运行/逐字节比对）
此前是**随机挂**的——同一份代码换个盐就错，`high/max/ultra` 都可能中招。修完后连续多轮
72/72 全绿。

**正确性覆盖**：`tests/v1211_features.php`（19 项）包含白盒断言（段收缩、无 `NOP`、
跳转目标是组首时指向超级指令、跳转目标落在组内时该组不被合并、异常表精确映射为
`[0, 3, 5]`）与真实产物回归（循环 / `goto` / 嵌套 `try-catch-finally` / 闭包 /
类方法 / 生成器，`high`+`max` × 3 盐，逐字节比对原生输出），外加 15.1 那四处缺陷的
定向用例（`global` + 块内函数 + 位与 + 裸块，`high`/`max`/`ultra` × 历史必挂盐 a3/a5）。
