# PERFORMANCE.md — 性能损耗对比

> 目标：把「混淆要付多少性能代价」从感觉变成**可复现的数字**，并给出选型建议。
> 所有数字由仓库内的 `tests/perf_bench.php` 现场跑出，可按文末命令复现。

---

## 1. 一句话结论

| 档位 | 运行时开销 | 结论 |
|---|---|---|
| `low` | **≈ 原生（1.1~1.2×）** | 可以直接上生产请求路径 |
| `mid` | **≈ 原生（1.4~1.5×）** | 可以直接上生产请求路径 |
| `high` | **百倍级（TP8 页面 0.8~1.4 s）** | 建议只用于高价值 / 低频路径，或前置缓存 |
| `max` / `ultra` | **千倍级** | 离线任务、授权校验、关键算法片段；不要挂在 QPS 路径上 |

**根因很单纯**：`high` 及以上才启用 **VM 虚拟机壳**——它把每条语句交给 PHP 写的解释器逐条执行，开销与「执行的语句数」成正比，而不是与「文件大小」成正比。`low` / `mid` 只有 token 级变换 + 一次性解码的编码壳，所以开销是常数级。

> 因此从 v1.1.0 起，**`low` / `mid` 预设不再包含 VM**：低中档的定位就是"性能优先"，要 VM 请上 `high`。

## 2. 测量方法（可复现）

```bash
# A) 混合负载：测 token 级档（low / mid）
php tests/perf_bench.php --runs=5 --levels=low,mid

# B) 轻负载：测 VM 档（high / max）——混合负载在 VM 下会跑上几分钟
php tests/perf_bench.php --runs=5 --levels=high,max --workload=tests/perf_workload_vm.php

# C) 开 CLI OPcache 再测一遍（贴近 FPM + OPcache 的生产环境）
php tests/perf_bench.php --runs=5 --levels=low,mid --opcache
```

工作量脚本 `tests/perf_workload.php` 覆盖：算术循环、用户函数调用、类方法调用、数组构造/排序/关联遍历、字符串拼接与哈希、递归、闭包、生成器。产物与原生**必须输出同一校验和**，否则该行标记 `✗`（语义被破坏时性能数字没有意义）。

指标口径：

| 指标 | 含义 |
|---|---|
| 冷启动总耗时 | `php <产物>` 的墙钟时间中位数，含 PHP 进程启动（本机 CLI 约 23 ms） |
| 纯计算耗时 | 工作量脚本内部 `hrtime` 自测，**不含**进程启动与解码，最能反映运行时开销 |
| 解码/编译开销 | 冷启动总耗时 − 纯计算 − 空脚本基线 ≈ 壳层解密 + eval 编译（FPM 下每请求都会付一次） |
| 峰值内存 | `memory_get_peak_usage(true)` |

测试环境：PHP 8.5.12 CLI（OPcache 关）、单核容器、Ubuntu 22.04。**绝对数值只在同机对比时有意义**，倍数关系可跨机参考。

## 3. 运行时开销：混合负载（token 级档）

源文件 3.2 KB，原生纯计算 8.4 ms。`--runs=3` 中位数：

| 变体 | 产物体积 | 构建耗时 | 冷启动总耗时 | 纯计算耗时 | 解码/编译开销 | 峰值内存 | 计算相对原生 | 语义一致 |
|---|---:|---:|---:|---:|---:|---:|---:|:---:|
| 原生（未混淆） | 3.2 KB | — | 33.4 ms | 8.4 ms | 2.2 ms | 2.00 MB | 1.00× | ✓ |
| `low` | 2.4 KB | 91 ms | 33.6 ms | 9.9 ms | 1.0 ms | 2.00 MB | **1.17×** | ✓ |
| `mid` | 6.0 KB | 215 ms | 35.8 ms | 12.6 ms | 0.4 ms | 2.00 MB | **1.49×** | ✓ |
| `high` | 47.5 KB | 552 ms | > 180 s（超上限） | — | — | — | — | — |
| `max` | 61.4 KB | 730 ms | > 180 s（超上限） | — | — | — | — | — |

`high` / `max` 超时不是基准缺陷，而是结论本身：**同一份 8.4 ms 的负载，VM 档需要数分钟**。所以 VM 档改用下面的轻负载单独测。

> `low` 的产物体积比源码还小，是因为 `low` 含 GZ 压缩壳：源码压缩后比原文更短。体积小 ≠ 保护弱，但**体积小确实意味着解码更快**。

## 4. 运行时开销：VM 档

轻负载 `tests/perf_workload_vm.php`（1.8 KB，原生纯计算 1.0 ms）：

| 变体 | 产物体积 | 构建耗时 | 冷启动总耗时 | 纯计算耗时 | 解码/编译开销 | 峰值内存 | 计算相对原生 | 语义一致 |
|---|---:|---:|---:|---:|---:|---:|---:|:---:|
| 原生（未混淆） | 1.8 KB | — | 24.7 ms | 1.0 ms | 0.2 ms | 2.00 MB | 1.00× | ✓ |
| `high` | 89.4 KB | 492 ms | 9,926 ms | 9,883 ms | 19.0 ms | 6.00 MB | **10,210×** | ✓ |
| `max` | 111.9 KB | 674 ms | 15,422 ms | 15,265 ms | 133.6 ms | 6.00 MB | **15,769×** | ✓ |

倍数看着夸张，是因为这份负载**几乎全是纯计算与函数调用**（没有任何 IO、没有框架开销）。真实业务代码里框架启动、DB、模板渲染占大头，倍数会被稀释——见下一节的 TP8 实测。

## 5. 真实项目：ThinkPHP 8 页面延迟

同一套 TP8 示例（22 文件 / 16 类），原版与混淆版各起一个 `php -S` 服务，同一份数据，`curl` 各打 8 次取中位数：

| 端点 | 原生 | `thinkphp8.config.php`（= high + VM） | 倍数 |
|---|---:|---:|---:|
| `GET /shop/products` | 1.84 ms | 832 ms | ~450× |
| `GET /shop/calc` | 2.57 ms | 1,382 ms | ~540× |
| `GET /shop/review-stats` | 30.4 ms | 888 ms | ~29× |

两点观察：

1. **绝对延迟落在 0.8~1.4 s**，不是分钟级——因为 TP8 页面真正的开销大头（框架启动、DB、渲染）在 VM 之外，VM 只解释业务代码那部分。
2. `review-stats` 本身较慢（30 ms），倍数反而最小（29×）：**原生越慢的路径，VM 的相对代价越低**（固定开销被摊薄）。

> 这个量级**不适合直接挂在高 QPS 的 Web 请求上**。要么用 `low` / `mid`，要么在 `high` 前面加页面缓存 / 异步化。

## 6. 开销归因：钱花在哪个开关上

同一份「20 万次算术循环」负载（原生纯计算 1.4 ms，进程启动基线 ~23 ms），逐个开关单独打开：

| 变体 | 冷启动总耗时 | 相对原生 | 说明 |
|---|---:|---:|---|
| 原生 | 24 ms | 1.0× | 基线（含 23 ms 进程启动） |
| 仅变量改名 `--var-length=8` | 25 ms | ~1.0× | **几乎免费** |
| 变量改名 + `--junk-runtime`（强度 8） | 25 ms | ~1.0× | 运行时垃圾可忽略 |
| `--vm`（裸 VM） | 1,640 ms | ~68× | **VM 一开就跳两个数量级** |
| `--vm --vm-junk=80` | 1,991 ms | ~83× | 字节码垃圾真实执行，+21% |
| `--vm --vm-p8` | 1,596 ms | ~66× | morph/keychain/builtinReplace 基本不加运行时 |
| `--vm --vm-junk=80 --vm-p8` | 2,240 ms | ~93× | 叠加后约 +37% |
| 预设 `low` | 25 ms | ~1.0× | 无 VM |
| 预设 `mid` | 26 ms | ~1.1× | 无 VM |
| 预设 `high` | 1,860 ms | ~78× | VM + junk=80 + stateMachine |
| 预设 `max` | 2,268 ms | ~95× | junk=160 + 全套反检测 |

结论：

- **VM 是唯一"数量级"开关**，其余（变量/函数改名、字符串 XOR、控制流、垃圾注入、语义变换、逐层壳）都是**常数级或可忽略**。
- `--vm-junk` 是 VM 内部唯一明显加运行时成本的参数（垃圾指令是**真执行**的，不是跳过）。
- `morph` / `keychain` / `builtinReplace` / `probe` / `fakeFog` 主要加**体积与构建时间**，运行时几乎不变——这几个是"性价比最高"的加固项。
- `--vm-probe` 的探针、`anti_debug` / `anti_tamper` 自校验是**每请求一次**的固定成本，不随业务量线性增长。

## 7. 构建耗时与产物体积

| 档位 | 3.2 KB 源文件 | 22 文件 TP8 app |
|---|---:|---:|
| `low` | 91 ms → 2.4 KB | — |
| `mid` | 215 ms → 6.0 KB | — |
| `high` | 552 ms → 47.5 KB | 9.4 s → 2.6 MB |
| `max` | 730 ms → 61.4 KB | 数十秒（fakeFog=160 / junk=160） |

- 体积膨胀主要来自 VM 字节码 + 诱饵函数 + 编码壳（base64 后约 1.33×，GZ 会压回去一部分）。
- 构建耗时随 `fakeFog` / `junk` / `layers` 线性上升；`ultra`（嵌套 VM）最慢，只建议离线跑一次。

## 8. 选型建议

| 场景 | 建议 | 理由 |
|---|---|---|
| 高频 Web 接口、内部系统 | `low` 或 `mid` | 开销 ≈ 原生，token 级混淆已能挡住"直接读源码" |
| 对外分发的组件 / SDK | `high` | 值得付百倍代价换取 VM 保护 |
| 授权校验、计费算法等核心片段 | `max`（只混淆该文件，其余用 `mid`） | 把 VM 代价限制在少量文件上 |
| CLI 批处理 / 离线任务 | `max` / `ultra` | 不在乎运行时，追求最强保护 |
| 框架项目（ThinkPHP / Laravel 等） | `other/thinkphp8.config.php` 或一键脚本 | 预设档**不含框架白名单**，直接用会出现"控制器不存在"这类问题 |

**分层混搭**是最实用的做法：把 `max` 只压在少数核心文件上，其余文件走 `mid`。

```bash
# 核心文件强保护
php entry.php --input=app/service/PriceCalculator.php \
    --output=dist/service/PriceCalculator.php --level=max --salt=$SALT

# 其余文件低成本混淆
php entry.php --input=app/controller --output=dist/controller --level=mid --salt=$SALT
```

## 9. 已知性能特性（不是 bug，是设计）

1. **VM 开销 ∝ 执行语句数**，与文件大小关系不大——一个被调用 10 万次的小函数比一个只加载一次的大文件贵得多。
2. **函数/方法调用是 VM 最贵的操作**（帧建立 + 参数绑定 + 引用回写）。调用密集的代码在 `high` 下会显著放大。
3. **生成器 / 大数组**在 VM 下内存占用更高（实测峰值 6 MB vs 原生 2 MB）。
4. **解码是每请求一次**：无 OPcache 时 eval 的代码不进字节码缓存，FPM 下每个请求都要重新解密 + 编译外层壳。若 QPS 高，务必开 OPcache 并考虑 `--opcache` 预热。
5. 想关掉某个拖慢的开关：`--vm-junk=0`、`--no-vm-cpool`、`--no-newline-poison`、`--no-shell-shield`（后者最影响体积与解码时间）。
