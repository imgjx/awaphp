# PERFORMANCE.md — 性能损耗对比

> 目标：把「混淆要付多少性能代价」从感觉变成**可复现的数字**，并给出选型建议。
> 本文数据为 **v1.1.1** 实测（本机 CLI、单核容器、PHP 8.5.12、OPcache 关）。
> 复现命令见第 2 节。

---

## 1. 一句话结论

| 档位 | 运行时开销（TP8 真实接口） | 结论 |
|---|---|---|
| `min` | **≤1.28×**（实测纯计算 1.01×；TP8 2.0 → 1.6 ms） | 词法替换 + 字符串简单 XOR 解密挡人，**无反调试 / 无壳**，损耗远在 1.28× 内 |
| `low` | **~2.8×**（→ 5.7 ms） | 可以直接上生产请求路径 |
| `mid` | **~6.2×**（→ 12.4 ms） | 可以直接上生产请求路径 |
| `high` | **~22×**（→ 44 ms） | 可用；建议只压核心文件，或前置页面缓存 |
| `max` / `ultra` | **~196× / ~242×**（→ 391 / 485 ms） | 离线任务、授权校验、关键算法片段；不要挂在高 QPS 路径上 |

**根因很单纯**：`high` 及以上才启用 **VM 虚拟机壳**——它把每条语句交给 PHP 写的解释器逐条执行，开销与「执行的语句数」成正比，而不是与「文件大小」成正比。`min` / `low` / `mid` 只有 token 级变换（`min` 连编码壳都没有），所以开销是常数级。

> 三个前提要一起看：
> 1. `min` / `low` / `mid` 三档**均不含 VM**（性能优先），要 VM 请上 `high`。
> 2. 从 v1.1.1 起 `low` / `mid` 的 token 级变换**大幅加强**（函数/类名、数字与字符串编码、
>    控制流 + GOTO、语义改写、运行时垃圾、诱饵注释、token 形态、EVAL/GZ 多壳），所以
>    它们的倍数比 1.1.0 的"轻量版"高，但仍然落在**个位数到十几毫秒**的绝对量级。
> 3. 从 v1.1.2 起新增 `min`：变量名 / 数字形态 / 字符串 base64+XOR 简单解密 / 去注释 / 压空白，
>    **无反调试探针、无壳、无复杂派生解密**（解密是固定密钥异或的简单逻辑）；性能损耗硬约束 **≤1.28×**
>    （原生跑 100 ms，开 `min` 必须 < 128 ms），实测纯计算 1.01×、冷启动 1.05×，远在上限内。

## 2. 测量方法（可复现）

```bash
# A) 混合负载：测 token 级档（low / mid）
php tests/perf_bench.php --runs=5 --levels=min,low,mid

# B) 轻负载：测 VM 档（high / max）——混合负载在 VM 下会跑上几分钟
php tests/perf_bench.php --runs=5 --levels=high,max --workload=tests/perf_workload_vm.php

# C) 开 CLI OPcache 再测一遍（贴近 FPM + OPcache 的生产环境）
php tests/perf_bench.php --runs=5 --levels=low,mid --opcache
```

工作量脚本 `tests/perf_workload.php`（3.2 KB）覆盖：算术循环、用户函数调用、类方法调用、
数组构造/排序/关联遍历、字符串拼接与哈希、递归、闭包、生成器。产物与原生**必须输出同一
校验和**，否则该行标记 `✗`（语义被破坏时性能数字没有意义）。

指标口径：

| 指标 | 含义 |
|---|---|
| 冷启动总耗时 | `php <产物>` 的墙钟时间中位数，含 PHP 进程启动（本机 CLI 约 23 ms） |
| 纯计算耗时 | 工作量脚本内部 `hrtime` 自测，**不含**进程启动与解码，最能反映运行时开销 |
| 解码/编译开销 | 冷启动总耗时 − 纯计算 − 空脚本基线 ≈ 壳层解密 + eval 编译（FPM 下每请求都会付一次） |
| 峰值内存 | `memory_get_peak_usage(true)` |

**绝对数值只在同机对比时有意义**，倍数关系可跨机参考。

## 3. 运行时开销：混合负载（token 级档）

源文件 3.2 KB，原生纯计算 8.27 ms。3 次采样取中位数：

| 变体 | 产物体积 | 冷启动总耗时 | 纯计算耗时 | 计算相对原生 | 语义一致 |
|---|---:|---:|---:|---:|:---:|
| 原生（未混淆） | 3.2 KB | 32 ms | 8.27 ms | 1.00× | ✓ |
| `min` | 2.8 KB | 32.4 ms | 8.4 ms | **1.01×** | ✓ |
| `low` | 8.0 KB | 39 ms | 13.54 ms | **1.64×** | ✓ |
| `mid` | 16 KB | 38 ms | 14.43 ms | **1.74×** | ✓ |
| `high` | 82 KB | — | 167.8 s（单次实测） | ~20,000× | ✓ |

`high` 在这份负载上已经没法稳定采样（函数调用 + 字符串密集），但它**不是超时失败而是结论本身**：
VM 档请用下一节的轻负载衡量。实际使用中 VM 档只该压在被调用次数有限的核心文件上。

> 1.1.0 的 `low` / `mid` 是 1.17× / 1.49×，但那两档当时几乎没有 token 级变换。v1.1.1 把
> 「不随语句数增长」的保护全堆上之后是 1.64× / 1.74× —— 用不到 1 毫秒的纯计算增量，
> 换来函数名/类名/字符串/数字/控制流/形态全套混淆 + 多层壳。

## 4. 运行时开销：VM 档（含 1.1.0 → 1.1.1 解释器提速）

轻负载 `tests/perf_workload_vm.php`（1.8 KB，原生纯计算 **0.919 ms**），3 次采样中位数：

| 变体 | 1.1.0 纯计算 | 1.1.1 纯计算 | 相对原生 | 语义一致 |
|---|---:|---:|---:|:---:|
| 原生 | 0.919 ms | 0.919 ms | 1.00× | — |
| `high` | 10,244 ms | **5,676 ms** | 6,176× | ✓ |
| `max` | 14,476 ms | **8,120 ms** | 8,836× | ✓ |

同一份产物在「20 万次 while 循环」这类**状态机派发密集**负载上（原生 1.20 ms）：

| 档位 | 1.1.0 | 1.1.1 | 提速 |
|---|---:|---:|---:|
| `high` | 5,655 ms | **2,198 ms** | **2.6×** |
| `max` | 6,769 ms | **2,678 ms** | **2.5×** |

提速来自两处（都在解释器热路径上）：

1. **操作数栈编码类型化**（占旧实现 VM 总耗时约 75%）：旧版把**每个**压栈值 `serialize()`
   后用 `str_repeat` + `substr` 现算 XOR 掩码、出栈再 `unserialize()`；新版按类型分流——
   int 走单次整型 XOR、string 走单次串 XOR（掩码从 8 KB 预算 pad 取）、float/bool/null 直存、
   array 才 serialize、不可序列化值落明文槽。解码内联进 `MCPOP`/`MCPEEK`，省掉一次闭包调用
   （≈ 26 ns/指令）。
2. **状态机派发压缩**：新增 `DISPATCH` / `SET_ST` 两条专用指令，把
   `PUSH_V st; PUSH_C s; EQ; JZ 1; JMP` 五条压成一条、状态写入两条压成一条。

倍数看着夸张（数千倍），是因为这份负载**几乎全是纯计算与函数调用**（没有 IO、没有框架开销）。
真实业务代码里框架启动、DB、模板渲染占大头，倍数会被稀释——见下一节。

## 5. 真实项目：ThinkPHP 8 页面延迟（v1.1.1 五档）

同一套 TP8 示例（22 文件 / 16 类，含 ORM / 事务 / 缓存 / 中间件 / 验证器 / 事件），
原版与混淆版各起一个 `php -S`、各用**自己的 SQLite 库**、同一份 seed 数据，
`GET /shop/products`（缓存 + 获取器 + JSON 字段 + 关联统计）取 5 次中位数：

| 变体 | 延迟 | 相对原生 | 产物体积 |
|---|---:|---:|---:|
| 原生 | 2.0 ms | 1.0× | — |
| `min` | **1.6 ms** | **0.8×（更快）** | 104 KB |
| `low` | 5.7 ms | 2.8× | 228 KB |
| `mid` | 12.4 ms | 6.2× | 412 KB |
| `high` | 44 ms | 22× | 2.1 MB |
| `max` | 391 ms | 196× | 3.3 MB |
| `ultra` | 485 ms | 242× | 6.8 MB |

> `min` **比原生还快**不是测量错误：它做了「去注释 + 压空白」，PHP 解析与 opcache 编译的
> 字节数变少，而新增成本只是常数级的 `base64_decode` + 一次 `XOR`（每串一次，文件头一条
> `hash` 装密钥），与去注释/压空白省下的编译字节数相抵，净收益为正。这也意味着 `min` 是
> **唯一可以无脑全站铺开**的档位——它**无反调试探针、无 `eval`、无 `gzinflate`、无输出缓冲**，
> 解密是固定密钥异或的简单逻辑，运行时仍是普通 PHP 文件；性能损耗硬约束 **≤1.28×**。

> 两轮独立复测（各自独立库 + seed + 预热）以确认稳定性：`mid` 11.12 / 11.13、`high` 44.4 / 45.7、
> `max` 395 / 409、`ultra` 473 / 476（ms）；`low` 波动较大（6.3 / 8.2），因其解码成本已接近
> PHP 启动抖动本身。**`max` / `ultra` 的早期版本曾按 `high` 的倍率估算（~46× / ~60×），
> 实测比估算慢 5 倍**——多出来的 `anti_ast` / 蜜罐 / 换行缠绕 / 结构毒化 / 防篡改壳每请求都要
> 做一遍解码与完整性校验，这部分成本与业务代码量无关，是**每请求固定开销**。

三点观察：

1. **绝对延迟是毫秒级，不是分钟级**——TP8 页面真正的开销大头（框架启动、DB、渲染）在 VM
   之外，VM 只解释业务代码那部分。50 ms 级延迟对后台/内部系统完全可接受。
2. **`min` 与原生同速甚至更快**，`low` / `mid` 落在 **6~12 ms**，与原生同处一个量级，
   可直接挂生产请求路径。`high` 的 44 ms 仍属可接受；`max` / `ultra` 的 391~485 ms 是
   **每请求固定开销**（多层壳解码 + 完整性校验），适合低频高价值入口，不适合高频接口——
   它们的定位本就是「单文件 / 核心算法」而非整站。
3. 11 个端点在**六档下全部逐字节等价**（含 POST、缓存、聚合、签名中间件 401 分支），
   说明这些数字对应的产物是**语义正确**的。早期的 high/max 空正文问题已在 1.1.1 修复
   （见 CHANGELOG）。

## 6. 开销归因：钱花在哪个开关上

同一份「20 万次算术循环」负载（原生纯计算 1.4 ms，进程启动基线 ~23 ms），逐个开关单独打开：

| 变体 | 冷启动总耗时 | 相对原生 | 说明 |
|---|---:|---:|---|
| 原生 | 24 ms | 1.0× | 基线（含 23 ms 进程启动） |
| 仅变量改名 `--var-length=8` | 25 ms | ~1.0× | **几乎免费** |
| 变量改名 + `--junk-runtime`（强度 8） | 25 ms | ~1.0× | 运行时垃圾可忽略 |
| `--vm`（裸 VM） | 1,640 ms | ~68× | **VM 一开就跳两个数量级** |
| `--vm --vm-junk=80` | 1,991 ms | ~83× | 字节码垃圾真实执行，+21% |
| `--vm --vm-p8` | 1,596 ms | ~66× | morph/keychain/builtinReplace 基本不加运行时 |
| `--vm --vm-junk=80 --vm-p8` | 2,240 ms | ~93× | 叠加后约 +37% |
| 预设 `low` | 25 ms | ~1.0× | 无 VM |
| 预设 `mid` | 26 ms | ~1.1× | 无 VM |

结论：

- **VM 是唯一"数量级"开关**，其余（变量/函数/类改名、字符串 XOR、数字编码、控制流 + GOTO、
  语义变换、运行时垃圾、逐层壳）都是**常数级或可忽略**——1.1.0 → 1.1.1 把 `low`/`mid`
  加到"几乎全开"，纯计算只从 1.17× 涨到 1.64× 就是证据。
- `--vm-junk` 是 VM 内部唯一明显加运行时成本的参数（垃圾指令是**真执行**的，不是跳过）。
- `morph` / `keychain` / `builtinReplace` / `probe` / `fakeFog` 主要加**体积与构建时间**，
  运行时几乎不变——这几个是"性价比最高"的加固项。
- `--vm-probe` 的探针、`anti_debug` / `anti_tamper` 自校验是**每请求一次**的固定成本，
  不随业务量线性增长。

## 7. 构建耗时与产物体积（TP8 示例 22 文件）

| 档位 | 构建耗时 | 产物体积 |
|---|---:|---:|
| `low` | 5.1 s | 228 KB |
| `mid` | 10.3 s | 412 KB |
| `high` | 9.0 s | 2.1 MB |
| `max` | 14.2 s | 3.3 MB |
| `ultra` | 15.0 s | 6.9 MB |

- 体积膨胀主要来自 VM 字节码 + 诱饵函数 + 编码壳（base64 后约 1.33×，GZ 会压回去一部分）。
- 构建耗时随 `fakeFog` / `junk` / `layers` 上升；`ultra`（嵌套 VM）最慢，只建议离线跑一次。
- `salt` 不同会让 `fakeFog` / 诱饵的随机量变化，同档体积可在 **±40%** 内浮动（既有特性）。

## 8. 选型建议

| 场景 | 建议 | 理由 |
|---|---|---|
| 高频 Web 接口、内部系统 | `low` 或 `mid` | 毫秒级开销，但已含函数/类/字符串/数字/控制流全套混淆与多层壳 |
| 对外分发的组件 / SDK | `high` | 值得付数十倍代价换取 VM 保护 |
| 授权校验、计费算法等核心片段 | `max`（只混淆该文件，其余用 `mid`） | 把 VM 代价限制在少量文件上 |
| CLI 批处理 / 离线任务 | `max` / `ultra` | 不在乎运行时，追求最强保护 |
| 框架项目（ThinkPHP / Laravel 等） | 直接用预设即可（五档均已验证） | v1.1.1 起预设默认保留属性名/参数名，框架按名读写的属性与路由参数不会被破坏 |

**分层混搭**是最实用的做法：把 `max` 只压在少数核心文件上，其余文件走 `mid`。

```bash
# 核心文件强保护
php entry.php --input=app/service/PriceCalculator.php \
    --output=dist/service/PriceCalculator.php --level=max --salt=$SALT

# 其余文件低成本混淆
php entry.php --input=app/controller --output=dist/controller --level=mid --salt=$SALT
```

## 9. 已知性能特性（不是 bug，是设计）

1. **VM 开销 ∝ 执行语句数**，与文件大小关系不大——一个被调用 10 万次的小函数比一个只加载一次的大文件贵得多。
2. **函数/方法调用是 VM 最贵的操作**（帧建立 + 参数绑定 + 引用回写）。调用密集的代码在 `high` 下会显著放大。
3. **生成器 / 大数组**在 VM 下内存占用更高（实测峰值 6 MB vs 原生 2 MB）。
4. **解码是每请求一次**：无 OPcache 时 eval 的代码不进字节码缓存，FPM 下每个请求都要重新解密 + 编译外层壳。若 QPS 高，务必开 OPcache 并考虑 `--opcache` 预热。
5. 想关掉某个拖慢的开关：`--vm-junk=0`、`--no-vm-cpool`、`--no-newline-poison`、`--no-shell-shield`（后者最影响体积与解码时间）。
6. **VM 档下用户函数被编译为字节码**，不再是 PHP 函数：`function_exists()` / 字符串回调
   （`call_user_func('name')`）由 VM 内部解析（v1.1.1 起兼容 `App\Util\name` 这类绝对名）。
   依赖反射遍历用户函数的代码在 VM 档下会看不到它们——这类代码请用 `low` / `mid`。
