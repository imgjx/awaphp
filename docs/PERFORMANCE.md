# PERFORMANCE.md — 性能开销实测

**简体中文** · [English](en/PERFORMANCE.md)

> 口径：**v1.2.11**，PHP 8.5.12 CLI，单核容器，OPcache 关，`salt` 固定（同 salt 产物可逐字节复现）。
> 本文只描述**当前版本**的行为；所有数字都可用第 2 节的命令重跑。
> 绝对毫秒只在同机对比时有意义，**倍数**可跨机参考。

---

## 1. 一句话结论

| 档位 | 真实项目页面（TP8 `/shop/calc`） | 纯计算微基准 | 定位 |
|---|---:|---:|---|
| `min` | **1.4×**（3.4 → 4.8 ms） | 1.0× | 无反调试 / 无壳 / 无 `eval`，可全站铺开 |
| `low` | **9.2×**（→ 31 ms） | — | token 级全套 + 多层壳，请求路径可用 |
| `mid` | **25×**（→ 83 ms） | — | 同上 + 状态机 / 蜜罐 / 防篡改，后台与内部系统可用 |
| `high` | **52×**（→ 174 ms） | **12.9×** | 单层 VM；只压核心文件，或前置缓存 |
| `max` | **73×**（→ 245 ms） | **12.9×** | 单层 VM + 全套壳，核心文件 / 授权校验 |
| `ultra` | **212×**（→ 713 ms） | **286×** | 嵌套 VM，离线任务与关键算法片段 |

三条要点：

1. **`high` 起步才有 VM**，它的开销与「执行语句数」成正比，与文件大小基本无关。
2. **`max` 与 `high` 的纯计算开销相同**（12.9×）：多出来的 1.4 倍差距全在**每请求一次的壳层解码与完整性校验**上，不在业务代码。
3. **`ultra` 比 `high` 贵 20 倍以上**：嵌套 VM + 多层状态机，解释器套解释器。它只适合低频入口。

## 2. 测量方法（可复现）

```bash
# A) 真实项目：TP8 整站 25 个 PHP 文件（app/ + route/ + view/）
unzip -q tests/tptest.zip -d /tmp/tp8 && cd /tmp/tp8/tp8
php /workspace/entry.php --input=app   --output=app_obf   --level=high --salt=tp8perf
php /workspace/entry.php --input=route --output=route_obf --level=high --salt=tp8perf
php /workspace/entry.php --input=view  --output=view_obf  --level=high --salt=tp8perf
rm -rf app route view && mv app_obf app && mv route_obf route && mv view_obf view
php -S 127.0.0.1:8090 -t public public/router.php   # 每档独立副本 + 独立 SQLite
curl -s -o /dev/null -w '%{time_total}\n' 'http://127.0.0.1:8090/shop/calc?base=100&qty=5'

# B) 纯计算微基准（VM 档）
php tests/perf_bench.php --runs=5 --levels=high,max,ultra --workload=tests/perf_workload_vm.php

# C) 超级指令开 / 关对照
php tests/perf_bench.php --runs=5 --levels=high --workload=tests/perf_workload_vm.php
php entry.php --input=tests/perf_workload_vm.php --output=/tmp/off.php -high --salt=perf-bench-v1 --no-vm-super-isa
```

指标口径：

| 指标 | 含义 |
|---|---|
| 冷启动总耗时 | `php <产物>` 的墙钟中位数，含 PHP 进程启动（本机 CLI ≈ 28.7 ms） |
| 纯计算耗时 | 负载脚本内部 `hrtime` 自测，**不含**进程启动与解码 |
| 解码/编译开销 | 冷启动 − 纯计算 − 空脚本基线 ≈ 壳层解密 + `eval` 编译（每请求一次） |
| 峰值内存 | `memory_get_peak_usage(false)`（精确字节；`true` 会按分配块取整，几 MB 内的差异看不出来） |

所有变体与原生**必须输出同一校验和**，否则该行作废——语义被破坏时性能数字没有意义。

## 3. 真实项目：ThinkPHP 8 整站（25 文件 / 16 类，含 ORM、缓存、中间件、验证器、事件）

原版与每档混淆版**各自一份副本、各自一个 SQLite 库**，同一份 seed 数据，`php -S` 单进程，每个端点预热一次后取 5 次中位数：

| 变体 | 构建耗时 | 混淆后体积 | `/shop/calc` | 相对原生 | `/shop/dashboard` | 相对原生 |
|---|---:|---:|---:|---:|---:|---:|
| 原生 | — | — | 3.36 ms | 1.00× | 2.75 ms | 1.00× |
| `min` | 0.24 s | 132 KB | 4.8 ms | 1.43× | 4.0 ms | 1.45× |
| `low` | 13.2 s | 780 KB | 31.0 ms | 9.2× | 26.1 ms | 9.5× |
| `mid` | 27.7 s | 1.26 MB | 83.2 ms | 24.8× | 65.0 ms | 23.6× |
| `high` | 31.1 s | 3.19 MB | 173.5 ms | 51.6× | 123 ms | 44.7× |
| `max` | 33.1 s | 4.66 MB | 245 ms | 72.9× | 178 ms | 64.7× |
| `ultra` | 44.8 s | 13.25 MB | 713 ms | 212× | 553 ms | 201× |

`/shop/calc` 是纯计算型接口（排序、去重、汇率分桶、空安全链），`/shop/dashboard` 是模板渲染页（约 200 行 PHP/HTML 混写）。六档产物在两个端点上都与原生**逐字节一致**。

**`low` / `mid` 的开销来自 `logic` 层的恒等式积木，而不是壳层解密。** 它把字面量与比较改写成 `__mod_sha1()` / `__mod_strlen()` 组成的恒等式，用来打断静态求值；一旦这个积木落进**循环条件或循环体**，就会变成每轮一次哈希。直接量级：

| 2000 次 `$sum += $i` 的空循环 | 循环净耗时 |
|---|---:|
| 原生 | 0.02 ms |
| `low` | **180 ms**（90 µs/轮） |
| `mid` | **295 ms** |
| `low` 去掉 `logic` 层 | 0.02 ms |

这也是「纯计算微基准上 `low` 能到数千倍、而真实页面只有 9 倍」的原因：业务代码的循环次数远小于微基准。**循环密集的自研算法请用 `high`**（VM 在编译期把这类常量积木折叠掉，实测 12.9×），或在 `low`/`mid` 上把 `logic` 强度降到 1。

## 4. 纯计算微基准：VM 档

`tests/perf_workload_vm.php`（1.9 KB：算术循环、函数、类方法、数组、字符串哈希、递归、闭包、生成器），原生纯计算 **1.31 ms**，5 次中位数：

| 变体 | 构建耗时 | 产物体积 | 冷启动总耗时 | 纯计算耗时 | 解码开销 | 峰值内存 | 相对原生 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 原生 | — | 1.9 KB | 28.8 ms | 1.31 ms | — | 716 KB | 1.00× |
| `high` | 1.78 s | 72.8 KB | 59.3 ms | 16.4 ms | 14.2 ms | 4.42 MB | **12.9×** |
| `max` | 1.73 s | 85.7 KB | 64.8 ms | 16.4 ms | 19.7 ms | 5.20 MB | **12.9×** |
| `ultra` | 1.62 s | 195.6 KB | 443.8 ms | 364.8 ms | 50.3 ms | 11.47 MB | **286×** |

- `high` 与 `max` 的**纯计算完全相同**：`max` 多出的 5.5 ms 冷启动是壳层解码 + 完整性校验，每请求一次、不随业务量增长。
- `ultra` 是嵌套 VM（外层解释器再解释内层派发），22 倍于 `high`。它的产物也最大（195 KB vs 73 KB）。
- 与真实页面的差距（12.9× vs 52×）说明：真实项目的耗时大头在框架启动、DB、模板，VM 只解释业务代码那一小段。

## 5. 超级指令：开 / 关 与 v1.2.10 → v1.2.11 对照

`--vm-super-isa` 把运行期高频的 2~4 条指令合并成一条新 opcode。v1.2.11 起被吸收的子指令**真删除**（v1.2.10 及以前用 `NOP` 占位），构建期重算段内跳转与异常表 pc。

**字节码条数**（同一份 workload、同一盐，构建期探针统计）：

| | 合并前 | 合并后 |
|---|---:|---:|
| v1.2.10 | 565 | 565（`NOP` 占位，条数不变） |
| v1.2.11 | 565 | **454（−19.6%）** |

**运行期**（`salt=perf-bench-v1`，15 轮交替采样取中位数，两轮独立实验）：

| 版本 | 超级指令 | 冷启动 `high` | 纯计算 `high` | 峰值内存 `high` | 冷启动 `max` | 峰值内存 `max` |
|---|---|---:|---:|---:|---:|---:|
| v1.2.10 | 开 | 60.9 ms | 16.96 ms | 3.96 MB | 62.7 ms | 4.75 MB |
| v1.2.10 | 关 | 61.3 ms | 17.02 ms | 3.96 MB | 62.6 ms | 4.74 MB |
| v1.2.11 | 开 | 61.8 ms | 16.73 ms | 4.64 MB | 66.1 ms | 5.45 MB |
| v1.2.11 | 关 | 62.1 ms | 16.78 ms | 4.62 MB | 64.1 ms | 5.44 MB |

**结论（这也是「新版是不是更费时」的答案）**：

1. **超级指令本身不费时**。同一版本内开/关的差：冷启动 −0.4~+0.4 ms、纯计算 −0.1~+0.3 ms，**都在噪声内**（同一产物重复跑 15 次的墙钟极差就有 ±1.5 ms）。真删省下的派发次数，被复合 handler 内部逐条解码子指令的成本抵平——这符合它的定位：**抗分析 + 零代价**，不是提速项。
2. **版本之间的内存差 +17%（3.96 → 4.64 MB）与超级指令无关**：把超级指令关掉，v1.2.11 仍是 4.62 MB。这笔账属于同一版里的 VM 语义修复（见 5.1）：以前退化成 `EVAL_STMT`（一条字符串交给原生 `eval`）的语句现在真编进字节码，几十条 opcode 数组比一个字符串贵得多。
3. **`max` 冷启动 +2~3 ms 是稳定可复现的**（66.1 / 64.1 vs 62.7 / 62.6），同样与超级指令无关（关掉也 +1.5 ms），来自解包期构造更大的指令数组。
4. **gz 后体积略增**：`NOP` 是 `[199][0]` 两字节的高度重复串，gzip 几乎不占空间；去掉后相邻字节熵升高。开超级指令的体积代价：`high` +56~+184 B、`max` +176~+964 B；v1.2.11 相对 v1.2.10 总体 +376 B（`high`）/ +1,448 B（`max`），即 **+0.5% / +1.7%**。

### 5.1 同一版里修掉的 VM 语义缺陷（它们的代价就是上面的内存）

| 缺陷 | 修法 | 代价 |
|---|---|---|
| 不透明载荷（`PHPRUN`）里的顶层变量落在闭包局部，函数内 `global $x` 读到 `null` | 执行前扫 `global` / `$GLOBALS['k']` 并预绑成引用 | 载荷扫描一次，可忽略 |
| 位与 `$a & $b` 编不过（只认 `NOT_FOLLOWED` token 形态） | 三种 `&` 形态都接受 | 无 |
| 裸块 `{ ... }` 不支持 | 按语句组递归编译 | 无 |
| `__NAMESPACE__` 不支持 | 编译期折值 | 无 |
| `funcsplit` 抽取含 `->` / `?->` / `::` 的语句，抽出来的是**原生**函数而 VM 类是 `stdClass` 代理 → `Call to undefined method` | 不再抽取这类语句 | 少一层打散 |

代价集中在「更多语句真的进了 VM」：`high` 峰值内存 +17%、`max` +15%，纯计算在噪声内。换来的是 `preset_e2e` 从「换个盐就随机挂」变成稳定 72/72。

## 6. 开销归因：钱花在哪个开关上

| 开关 | 量级 | 说明 |
|---|---|---|
| `shell:vm` | **数量级（10~50×）** | 唯一随执行语句数增长的开关；函数/方法调用是最贵的操作 |
| `logic`（`--logic-intensity`） | **0~数千×**，取决于积木落在哪里 | 落在循环条件/循环体里 = 每轮一次哈希；落在初始化段则可忽略 |
| `shell:gz` / `shell:eval` / `shell:anti_*` | **每请求固定 5~50 ms** | 解码 + 完整性校验，与业务量无关 |
| `--vm-junk` | +20% 左右 | 垃圾指令是**真执行**的，不是跳过 |
| `morph` / `keychain` / `builtinReplace` / `probe` / `fakeFog` | 运行期 ≈ 0 | 只加体积与构建时间，性价比最高的一档 |
| `constfold` | **负开销** | 构建期把字面量算完，运行期这段计算彻底消失 |
| `funcsplit` | +0.1~0.3 µs / 次调用 | 把内联语句换成一次函数调用；`level=3` 落在热循环里可测量 |
| `var` / `func` / `class` 改名 | ≈ 0 | 纯静态替换 |

## 7. 已知性能特性与规避

1. **`logic` 积木在热循环里**：`low` / `mid` 的恒等式会落进循环条件（`for ($i = 0; $i < (__mod_strlen(...)*50); $i++)`），每轮重算哈希。规避：`--logic-intensity=1`，或自定义配置去掉 `logic` 层，或改用 `high`（VM 编译期折叠）。
2. **解码是每请求一次**：无 OPcache 时 `eval` 的代码不进字节码缓存。QPS 高时务必开 OPcache（`--opcache` 预热），否则每请求都要重新解密 + 编译外层壳。
3. **`ultra` 只适合低频入口**：嵌套 VM 让纯计算到 286×、页面到 212×，产物 13 MB。单文件核心算法可用，整站不要用。
4. **VM 档下用户函数被编译为字节码**，不再是 PHP 函数：`function_exists()` / 字符串回调由 VM 内部解析；依赖反射遍历用户函数的代码请用 `low` / `mid`。
5. **生成器 / 大数组在 VM 下内存更高**：微基准峰值 4.4 MB vs 原生 0.7 MB（`high`），`ultra` 到 11.5 MB。
6. **整站混淆的函数名唯一化**：`logic` 注入的 `__mod_*` 积木经 `module_link` 内联后，函数名带**文件派生段**（`__ml<层><文件>_<名>`），多文件项目不会互相 `Cannot redeclare`。同一份源码同 salt 可复现。
7. 想关掉某个拖慢的开关：`--no-vm-super-isa`、`--vm-junk=0`、`--no-vm-cpool`、`--no-newline-poison`、`--no-shell-shield`（最后一项最影响体积与解码时间）。

## 8. 选型建议

| 场景 | 建议 | 理由 |
|---|---|---|
| 高频 Web 接口、内部系统 | `low` 或 `mid` | 9~25 倍，绝对延迟仍是几十毫秒；避开循环密集的自研算法 |
| 自研算法 / 循环密集代码 | `high` | VM 在编译期折叠常量积木，12.9× 反而比 `low` 的 90 µs/轮 便宜 |
| 对外分发的组件 / SDK | `high` | 单层 VM，代价可控，抗分析足够 |
| 授权校验、计费核心片段 | `max`（只压该文件） | VM + 全套壳，把代价限制在少量文件 |
| CLI 批处理 / 离线任务 | `max` / `ultra` | 不在乎运行时，追求最强保护 |
| 框架项目（ThinkPHP / Laravel） | 直接用预设 | 六档与原生逐字节等价，属性名/参数名默认保留 |

**分层混搭**最实用：核心文件 `max`，其余 `mid`。

```bash
php entry.php --input=app/service/PriceCalculator.php \
    --output=dist/service/PriceCalculator.php --level=max --salt=$SALT

php entry.php --input=app/controller --output=dist/controller --level=mid --salt=$SALT
```
